# Руководство по внесению вклада (Contributing)

Мы рады приветствовать любые улучшения, исправления ошибок и предложения новых функций в `async-yt-dlp`!

---

## 1. Ветвление в репозитории (Branching Strategy)

В проекте используется модель с двумя постоянными ветками:
- **`main`**: основная (production) ветка. Содержит только стабильные, готовые к релизу версии кода. Прямые коммиты в `main` запрещены; слияния происходят только из `develop` перед выпуском новой версии с простановкой тега версии (`vX.Y.Z`).
- **`develop`**: ветка активной разработки. В неё сливаются новые возможности и исправления через Pull Requests.
- **Временные ветки**:
  - `feature/<название>`: для разработки новых функций (создаются от `develop` и вливаются обратно в `develop`).
  - `fix/<описание>` или `bugfix/<описание>`: для исправления ошибок (создаются от `develop` и вливаются в `develop`).
  - `hotfix/<описание>`: критические исправления для продакшна (создаются от `main` и вливаются как в `main`, так и в `develop`).

## 2. Процесс разработки

1. Сделайте Fork или склонируйте репозиторий:
   ```bash
   git clone ssh://git@localhost:2222/6aton/AsyncYT-DLP.git
   cd AsyncYT-DLP
   ```
2. Создайте новую временную ветку от `develop`:
   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b feature/my-new-feature
   ```
3. Установите зависимости разработки:
   ```bash
   uv sync --extra dev
   ```
4. Внесите изменения, соблюдая соглашения по стилю кода и строгой типизации.
5. Добавьте тесты на новый функционал в каталоге `tests/`.
6. Отправьте ветку и создайте Pull Request в ветку `develop`.

---

## 2. Стандарты качества кода

Перед созданием Pull Request обязательно убедитесь, что все автоматические проверки проходят локально:

```bash
# Проверка форматирования и линтинга
uv run ruff check src/ tests/ examples/
uv run ruff format --check src/ tests/ examples/

# Проверка строгой типизации
uv run mypy src/

# Запуск тестов
uv run pytest tests/ -v -m "not integration"
```

---

## 3. Язык комментариев и документации

- Все комментарии к коду и docstrings должны быть написаны на русском языке.
- Все файлы документации в `docs/` и описание в `README.md` должны вестись на русском языке.
- Имена классов, методов, функций и переменных должны быть на английском языке в соответствии с PEP 8.
